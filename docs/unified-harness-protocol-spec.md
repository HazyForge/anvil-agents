# Unified Agent Harness Programmatic Protocol Specification

## 1. Problem Statement & Motivation
Currently, Anvil Agents interacts with runners primarily through static entrypoint bash scripts (`entrypoint.sh`) that invoke one-shot CLI commands (`codex exec`, `opencode run`, `hermes`, `openclaw agent`, `grok --prompt-file`, `pi -p @file`). 

While this model works for fire-and-forget headless jobs, it is inadequate for granular, interactive, mid-flight control:
- **Steering:** Injecting mid-turn user intent or feedback without tearing down the process.
- **Interrupting:** Halting generation cleanly mid-stream without terminating the Pod/Job.
- **Granular Inspection:** Querying active tools, thought processes, AST changes, and token consumption in real-time.
- **Dynamic Tooling / Capability Injection:** Calling tools and dynamic RPCs programmatically over a defined protocol rather than relying on CLI arguments or environment variables.

To make capabilities more granular across diverse agent harnesses (OpenCode, Hermes, OpenClaw, Grok, Pi, Codex, Claude Code, OpenHands, Aider, etc.), Anvil Agents implements a **Unified Programmatic Harness Protocol**.

## 2. Native Harness Protocol Matrix

Each major harness supports (or can expose via standard sidecar/adapter loop) a structured communication protocol:

| Harness / Engine | Native Protocol / Interface | Mechanism | Capabilities Supported |
| :--- | :--- | :--- | :--- |
| **OpenCode** | Server / JSON-RPC / REST API | `opencode serve` / headless event stream | Sessions, turn steering, step execution, tool approval, cancel |
| **Codex** | App Server / JSON-RPC over stdio/IPC | `codex app-server` | Structured turns, steering, interrupt, tool registration |
| **Hermes Agent** | Python In-Process / CLI API / Function calling | `hermes.chat` / Python API | Query streaming, programmatic tool dispatch, step hooks |
| **OpenClaw** | Gateway / Session WebSockets | `openclaw gateway` / JSON RPC | Multi-turn sessions, thinking level, streaming deltas |
| **Pi Coding Agent** | Session IPC / Event JSON | Node/TypeScript programmatic API (`@earendil-works/pi-coding-agent`) | Extension hooks, streaming thoughts, tool events |
| **Claude Code** | Stdio Streaming / ACP (Agent Client Protocol) | JSON-RPC / SSE over stdin/stdout | Structured steering, interrupt, tool call request/response |
| **OpenHands** | Event Stream API | REST + WebSocket (`/api/conversations/{id}/events`) | Action-Observation loop, step interrupt, turn injection |
| **Aider** | Input/Output IPC Pipe | Programmatic Python API / Pipe | Queue prompt, interrupt, commit hooks |

## 3. The Unified Programmatic Protocol (UPP) Contract

Anvil standardizes on a bidirectional streaming protocol hosted over a Unix Domain Socket (UDS) or loopback HTTP/SSE/WebSocket in the Pod at `/run/anvil/harness.sock` (or `http://127.0.0.1:4096`).

### 3.1 Message Envelope (JSON-RPC 2.0 / Event Stream)
Every message conforms to standard JSON-RPC 2.0 or structured Event Envelope:

```json
{
  "protocol": "anvil.harness/v1alpha1",
  "sessionId": "agent-run-xyz-session",
  "type": "event | request | response",
  "id": "msg-001",
  "name": "<action_or_event_name>",
  "payload": {},
  "timestamp": "2026-09-14T13:10:00.000Z"
}
```

### 3.2 Protocol Operations

#### A. Control Operations (`request` -> `response`)
1. **`harness.initialize`**: Handshakes with the harness, exchanges capabilities, supported tools, and session schema.
2. **`harness.turn.submit`**: Submits a prompt or turn with explicit role (`user`, `system`, `tool_result`).
3. **`harness.steer`**: Injects an in-flight prompt / hint while the harness is thinking.
4. **`harness.interrupt`**: Instructs the harness to stop the current generation/tool loop immediately, retain state, and yield an interrupt event.
5. **`harness.tool.execute`**: Dispatches external tool execution or requests client confirmation.

#### B. Streamed Events (`event`)
1. **`turn.delta`**: Text token chunk generated by the model.
2. **`thought.delta`**: Internal reasoning/thinking tokens (e.g. Grok, Claude, Pi).
3. **`tool.call.started`**: Harness requested tool execution (name, arguments, call ID).
4. **`tool.call.completed`**: Tool execution finished with output or error.
5. **`state.transition`**: Transition states: `idle` -> `planning` -> `executing` -> `waiting_input` -> `completed` -> `failed`.
6. **`status.report`**: Direct equivalent of `ANVIL_AGENT_RUN_STATUS_JSON` (`requestPeer`, `interruptDuplicate`, `progress`, `decision`).

## 4. Architectural Implementation in Anvil Runners

Instead of raw entrypoint bash executing a one-shot CLI command and terminating:
1. **Harness Adapter Daemon (`anvil-harness-adapter`)**:
   - Runs inside the runner pod (or sidecar).
   - Translates between the standard `/run/anvil/harness.sock` UPP protocol and the runner's native engine (e.g. Codex app-server, OpenCode server, Pi session API, or Python Hermes runner).
2. **Interactive Mailbox Connector**:
   - Watches `/run/anvil/chat/inbox/` for new steering utterances or interrupt flags written by API/Desktop chat.
   - Forwards them directly across the UPP socket into the active runner.
3. **Desktop & API Bridge**:
   - The desktop chat and always-on manager connect directly through the API stream, passing structured messages down to the harness protocol rather than relying on raw `exec`.
